# 每段对话怎样标注

先确认你看的批次与工作表对应，入口在 [本目录说明](README.md)。只看截取前原文，不找后续结局，不用完整对话摘要代替自己的判断。

## 先判断交接位置是否可用

当前原文是否足够说明用户在办什么？如果上下文太少或位置不合适，写清原因，不自行把某段往后挪。是否存在未完成事项要另判：一段对话可以截取位置清楚，但事情已经办完，仍不能纳入主要遗漏率实验。

## 逐件记录请求、进度和证据

把退款到账、运费承担等不同请求分开写，同一件事反复催促只算一件。每件都写明用户请求、怎样才算办完、目前状态和原文依据。

下面只是虚构格式示意，不能照抄成真实标注：

```text
用户想办的事：让退款到账。
怎样才算办完：实际收到退款。
目前状态：还没办完。
依据：第2句用户说没到账，第5句客服说仍在审核。
```

状态可以写还没办完、已经办完或看不出来。已受理不等于已到账；没看到完成记录也不一定证明未完成。原文证据不足就保留不确定。判断细节见 [研究规则](../01_研究说明/protocol_v0.2.md)。

至少有一件明确未决事项，且交接位置可用，才可以纳入；没有就不纳入，拿不准说明原因。两名标注者先各存一份，讨论和裁决另存版本。

## 整理到 JSON 时用这张表

中文表填写好后，逐项核对到程序读取的 JSON。两者目前不会自动同步。

| 中文内容 | JSON怎么填 |
| --- | --- |
| 填写人 | reviewer，姓名或固定代号 |
| 交接点是否可用 | cut_acceptable，可用 true，不可用 false |
| 是否纳入 | eligibility，可纳入 eligible；不可纳入 ineligible；不确定 uncertain；未检查 unreviewed |
| 原因 | reason，用中文说明 |
| 具体事项 | items，每件单独一项，item_id不重复 |
| 用户请求、完成标准 | request、endpoint |
| 事项状态 | status，未完成 open；已完成 resolved；不确定 uncertain |
| 依据 | evidence_indices填原文编号列表，evidence_note解释判断 |

原文编号从0开始。页面上的第5句在 JSON 中也是5，不再加1。只引用当前截取材料里的编号。导出时程序会检查字段和编号，但内容对不对仍由人工负责。
